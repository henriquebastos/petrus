# CV20 — Approachable Petrus

## Intent

Let a developer author, validate, run, observe, resume, and extend a durable
Petrus process from one coherent progressive surface while retaining canonical
artifacts, explicit durability and authority, and full lower-level control.

This is one Value because the promise is the whole developer journey. Separate
Values for authoring, a runner, presentation, examples, and agent convenience
would reproduce the current ownership seams instead of lowering cognitive cost.

## User promise

A developer can begin with one readable flow/application file, compile it to
the existing canonical Net, understand validation failures before motion, run
or resume it under an honestly named local profile, and inspect what happened.
As the application grows, the developer may replace stores, Dispatch, Workers,
presentation, and optional agent machinery without changing process semantics
or rewriting into another execution model.

## Delivery

1. [CV20.DS1 — One-file first motion](cv20-ds1-one-file-first-motion.md)
   will identify and deliver the smallest generic application/run composition
   after executing AX28 against the frozen runtime.
2. [CV20.DS2 — Expressive flow authoring](cv20-ds2-expressive-flow-authoring.md)
   will select a default domain-first authoring layer and prove deliberate
   descent to the low-level Net kernel.
3. [CV20.DS3 — Live understanding](cv20-ds3-live-understanding.md)
   will deliver the Petrus-owned portable definition/view/lineage contract and
   compose terminal, JSONL, and Arx understanding without entering execution.
   ES-061 supplies its accepted semantic Candidate.
4. [CV20.DS4 — Generated authoring and worked examples](cv20-ds4-generated-authoring-and-examples.md)
   will make generation, diagnostics, examples, and evaluation consume one
   selected public authoring contract without auto-executing generated source.
5. [CV20.DS5 — Approachable effects and agents](cv20-ds5-approachable-effects-and-agents.md)
   will make ordinary Activities and one honestly supported Agenticus profile
   approachable leaves while preserving different authority needs.

DS1 is the first general journey pull. DS3's portable-document and static V5
arrangement slice may be expanded independently because ES-061 already bounds
definition, view, lineage, and custody; its live-runtime join waits for DS1's
concrete consumer. DS2 protects the authoring/descent seam before DS4 generates
against it. DS5 follows an ordinary zero-agent DS1 profile.

The Navigator pulled DS3's independent static slice on 2026-08-27. Its first
implementation unit is Done:
[CV20.DS3.TS1 — Portable definition and view document foundation](cv20-ds3-live-understanding/cv20-ds3-ts1-portable-definition-view/index.md).

## Architecture contract

- Progressive disclosure is a frontend over the existing Net, History,
  Activity, and authority model, never a smaller or second runtime.
- The Python DSL compiles authored specifications to canonical Net artifacts;
  Python frames, generators, coroutines, and agent threads are not durable
  workflow state.
- One Instance keeps one append-only canonical History. Presentation and
  portable document lineage remain projections with explicit provenance.
- Petrus owns generic composition and protocol. Arx owns interactive human
  presentation. Applications own clients, credentials, domain policy, and
  effect authority.
- The ordinary zero-agent path must be coherent before agent convenience can
  claim approachability.

## Done condition

CV20 is Done when representative zero-agent and supported-agent applications,
including the Hamsterdan pressure test, demonstrate all of the following:

1. one readable flow/application source reaches compile, canonical inspection,
   validation, identified local motion, observation, replay, and resume under a
   named profile;
2. domain-first authoring and deliberate low-level descent compile to the same
   canonical model with local, actionable errors;
3. one Petrus portable document carries exact definition, optional view, and
   protected forkable execution lineage, and Arx round-trips a Hamsterdan-scale
   arrangement without changing Net identity;
4. generated packages and worked examples consume the selected diagnostics and
   authoring contract and are never executed merely because they were generated;
5. ordinary Activities and one supported Agenticus profile use the same journey
   while preserving their distinct authority and support boundaries; and
6. no convenience path hides durability, provider, placement, retry, failure,
   external-effect, or application-lifecycle ownership.

## Promotion evidence boundary

The Navigator's promotion creates a roadmap commitment; it does not claim that
ES-056's original AX27–AX29 and application acceptance gates already passed.
Those gates now belong to the relevant Delivery Stories and must be executed
before their contracts are accepted. ES-061's executable semantic evidence is
accepted specifically into DS3; its Arx V5 and application-bound execution
cases remain Delivery acceptance work.

## Out of scope

- Replacing canonical History with ordinary language control flow.
- Making Petrus an application lifecycle framework.
- Hiding credentials, state files, durability, or provider choices behind an
  unnamed easy mode.
- Promoting private CV10 execution seams or unsupported provider profiles.
- Copying Hamsterdan domain vocabulary into Petrus as a generic DSL.
- Production migration merely because an exploration or acceptance model runs.
